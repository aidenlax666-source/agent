# 架构详解（Architecture Deep-Dive）

本文深入拆解本项目的核心工程机制。适合面试讲技术深度时使用。

---

## 1. 核心思想：LLM-as-Compiler

传统上 LLM 应用是"提示词 → 文本输出"。本项目的核心是把 LLM 当作**编译器**：

```
自然语言需求  ──编译──▶  可执行脚本  ──运行──▶  产物  ──校验──▶  正确结果
（源代码）      （LLM）      （沙箱）             （四重检查）
```

编译器要做的三件事这里都有：
1. **词法/语法分析** → 需求结构化理解（分领域提示词模板）
2. **代码生成** → 生成 Python 脚本
3. **错误处理** → 校验失败 → 自愈 → 重编译（`mini_generator.py`）

### 四重校验（关键创新）

生成的脚本执行后，不能只看"退出码 0"就判定成功——那会放过大量假通过。项目对 stdout 约定机器可读标记，逐一校验：

| 校验 | 协议标记 | 拦截的问题 |
|---|---|---|
| 数量 | `DATA_ROWS:N` | 要求 100 条只抓了 3 条 |
| 字段 | `PREVIEW_DATA:[...]` | 漏了关键列/字段 |
| 功能覆盖 | 退出码 + 业务标记 | 主流程没跑到 |
| 数据值 | 抽样比对 | 值全错/格式化错误 |

任一项不过 → 把**具体失败原因**（不是笼统的"失败"）反馈给 reasoner 模型 → 生成修复 → 重跑。

## 2. apply_patch 协议（省输出 token 的核心）

### 问题

改一个已有文件时，如果让模型输出**整个文件**的新内容：
- 输出 token 与文件大小成正比（改 3 行也要输出 1000 行）
- 模型长输出容易"退化"（重复行、截断）——实测曾出现整段重复 3 次

### 方案

模型只输出**改动行**（类似代码评审补丁的写法）。

```
模型输出：
{
  "patch": {"main.py": [
    "@@ -1,3 +1,4 @@",
    " print('hello')",
    "-print('old')",
    "+print('new')"
  ]},
  "files": {"new_file.py": "完整内容"},   // 新增文件仍用完整内容
  "summary": "..."
}
```

为什么用**数组形式**而不是 unified diff 字符串？因为 JSON 字符串里嵌 `\n` 转义容易让模型出错；数组每个元素一行，无转义问题（实测数组形式远比字符串形式稳定）。

### 后端应用（`_dev_apply_patch`）

1. 解析 hunk（`@@ -旧起始行,旧行数 +新起始行,新行数 @@`）
2. **优先按行号定位**并验证上下文行一致
3. 行号不准 → `difflib.SequenceMatcher` **内容模糊匹配**（容忍模型数错行）
4. 应用 → 生成完整文件 → 后续校验/打包/下载流程完全不变（patch 对下游透明）

### 失败回退

patch 应用失败（定位不到）→ 把错误反馈给模型："请改用 files 字段输出完整内容" → 重试（最多 3 次）。**格式错误不抛给用户，而是自我纠正。**

## 3. 两阶段上下文（省输入 token）

### 问题

把整个项目（可能 100+ 文件）塞给模型：
- 输入 token 巨大
- 无关文件干扰判断

### 方案：文件清单 → 点菜 → 按需读取

**阶段 1**：只给文件清单（路径 + 字符数 + 首行预览，每文件 ~100 token），模型输出：

```json
{"files_to_read": ["order.py", "main.py"], "grep": ["billing_info"]}
```

**阶段 2**：只读取选中的文件完整内容 + grep 命中结果，再让模型改码。

### grep 搜索

模型可在阶段 1 输出 `grep` 数组（要定位的符号）。后端全文搜索（大小写不敏感），返回 `文件:行号: 行内容`，**命中文件自动并入读取清单**。

实测：17 文件项目中改 `billing_info` 函数签名，模型 grep 后精确定位到藏在 `report.py` 的调用点并同步修改——从"猜哪个文件相关"变成"搜到调用点"。

### 兜底

- 文件 ≤12 个：直接全量（避免多一次 LLM 往返）
- 模型选择失败/空选：回退全量上下文

## 4. 自愈引擎（失败不抛给用户）

### 命令执行失败 → 多轮修复

```
执行命令失败（第 N 次，共 5 次）
    │
    ▼
把完整 stderr 反馈给 reasoner 模型
    │
    ├─ 依赖编译失败 → 模型换实现方案（如 better-sqlite3 → sql.js 纯 JS）
    ├─ 代码/端口问题 → 模型输出 patch/files 修复
    ├─ 换思路更好 → 模型直接给新方案
    └─ 无法解决 → 模型输出 give_up + 原因（不瞎试）
    │
    ▼
应用修复 → 重跑 → 成功则结束
```

### 与"固定 3 次重试"的区别

不是机械重试：模型**知道还剩几次**、**可以换实现思路**、**可以明确放弃**。5 次仍失败说明方案本身不行，把原始错误返回给用户（而不是把工具链错误直接抛出来）。

## 5. 沙箱与安全（纵深防御）

### 执行隔离

```
Docker 可用 ──▶ 容器（无 privileged / 只读挂载 / 内存CPU限额 / bridge 网络 / 超时清理）
Docker 不可用 ──▶ 宿主回退（Windows 本地开发）+ AST 静态扫描（最后防线）
```

### AST 静态扫描（`sandbox/security.py`）

执行**前**对生成代码做抽象语法树分析，拦截：

- `eval / exec / compile / __import__`（动态执行）
- `os.system / popen / fork / spawn*`（命令注入）— 含 `getattr(os,"system")`、`os.__dict__["system"]`、`from os import system`、`builtins.eval` 等绕过形态
- SSRF：字符串常量里的内网/回环/云元数据地址（`127.0.0.1`、`169.254.169.254`、`10.x`…），域名会 **DNS 解析后按 IP 判定**
- 敏感文件读取：`open(".env")`、`Path("config.py").read_text()` 等
- 登录态外泄：沙箱注入的 `_AUTH`（用户登录 Cookie）只允许传给 `browser.new_context(storage_state=_AUTH)`，出现在 print/写盘/网络调用即拦
- 越权删除：`shutil.rmtree` 等作用于项目目录外路径时拦

### 为什么静态扫描 + 宿主回退是"纵深防御"而非"安全边界"

Windows 本地开发没有 Docker 时，脚本直接在宿主跑——**这本身不是隔离**。静态扫描是**best-effort 防线**（拦最明显的风险），真正的隔离来自 Docker。文档明确说明：生产环境必须启用 Docker。

### 云架构下的沙箱设计（多实例）

多实例部署时沙箱不能再用"每实例本地磁盘"，三个设计点（均向后兼容，不配=现状）：

1. **共享目录**：登录态（`SANDBOX_PROFILE_ROOT`）与产物（`ASSET_WEB_ROOT`）指向共享卷。
   否则用户在实例 A 登录、任务被实例 B 消费时读不到登录态，产物也跨实例不可见。
   路径统一走 `app/paths.py`（`profile_root` / `web_root` / `user_profile_dir`），
   不再散落硬编码相对路径。临时中转目录保持本地（产物最终落共享 web/）。

2. **全局并发**：`SANDBOX_GLOBAL_CONCURRENCY` > 0 且配 Redis 时，用 Redis 槽位信号量
   （`aiagent:sandbox:slot:{i}`，SETNX + TTL）做跨实例精确限制——总并发 = 配置值，
   而不是实例数 × 单实例并发。崩溃自动释放（TTL），本地信号量仍兜底本实例资源。

3. **孤儿沙箱回收**：容器打标签（`aiagent.worker`/`aiagent.task`），实例启动时调用
   `cleanup_orphan_containers()`：回收本实例遗留容器 + 任务租约已不存在的容器
   （宁可保守不可误杀，Redis 抖动时跳过）。

## 6. 自动化引擎（30s 调度器）

```
mini_scheduler_loop（30s 循环）
  ├─ 定时任务重跑（interval/daily）—— 稳定 key 防重叠 + 原子抢占
  ├─ 定时提醒（HH:MM）—— 去重（同 id 同分钟只发一次）
  └─ 监控任务（窗口标题/屏幕哈希）—— 冷却窗口 + 触发动作任务
```

- 窗口监控：ctypes 枚举窗口标题，零依赖
- 屏幕监控：Pillow 截图 → 16x16 灰度感知哈希 → 变化检测
- 触发动作：自然语言动作需求 → 走完整任务管线（LLM 生成+执行）

## 6.5 记忆系统（记住用户偏好）

用户偏好是"隐性需求"——用户说"做个 Excel"通常意味着"像上次那样"。系统自动维护用户级长期记忆：

### 自动提取（零成本正则优先）

任务成功收尾时，`_extract_memory` 从需求文本提取偏好：

- 显式表达：「我喜欢/习惯/偏好/每次都…」→ 记下短语
- 格式偏好：正则匹配 `excel/csv/中文/图表/word/英文` → 记下标准化偏好（如"输出用 Excel 格式"）

### 自动注入

任务开始时，把该用户最近 15 条记忆拼进需求上下文：

```
【用户偏好记忆】输出用 Excel 格式；用中文输出；…
（与本次需求冲突时以本次为准；无冲突默认按记忆执行）
```

### 存储与管理

- SQLite `user_memory` 表（user_id, kind, content, updated_at），主键 (user_id, content) 天然去重
- kind：preference(偏好) / habit(习惯) / fact(事实)
- 上限 50 条，超限淘汰最旧
- `/memory` 页面：查看 / 手动添加 / 单条删除 / 清空（用户始终能看见 AI 记住了什么）

## 7. 关键设计决策记录（ADR）

| 决策 | 为什么 |
|---|---|
| SQLite + 参数化 + 字段白名单 | 单机部署够用；杜绝 SQL 注入（动态字段名只来自白名单） |
| 产物页与 API 不同源 | 防同源 XSS 偷取 localStorage JWT |
| 匿名身份绑定 IP | 防 X-Anonymous-Id 冒用他人匿名数据 |
| 积分原子扣减（`UPDATE WHERE credits>=?`） | 防并发透支 |
| 多 key 轮询 + 429 退避 | DeepSeek 限流下的可用性 |
| patch 数组形式而非 diff 字符串 | JSON 转义稳定性（实测） |
| 记忆自动提取用正则而非每次 LLM | 零成本；显式偏好表达已覆盖主要场景，误提取概率低 |
| 登录态短时存储（2h TTL） | 第三方 Cookie 会过期，永久保存无意义且有安全残留 |
